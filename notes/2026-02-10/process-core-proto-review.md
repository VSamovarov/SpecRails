## 🎯 Что это и зачем

`process-core-proto` — **работающий прототип ядра SpecRails** для эксперимента с генерацией бизнес-процессов из текста.

### Главная цель
Проверить идею: **можно ли превратить AI из "черного ящика" в инженерный инструмент** с чёткими контрактами и проверяемыми результатами.

### Что решает
1. **Проблема непредсказуемости AI** — вводим формальные контракты (JSON Schema) для ответа AI
2. **Проблема доверия к AI** — двухэтапная проверка (схема + семантика)
3. **Проблема исправления ошибок** — repair loop с явной передачей ошибок обратно в AI
4. **Изоляция AI зависимостей** — AI спрятан за интерфейс `AiProvider`, ядро детерминировано

## 🏗️ Архитектура прототипа

### Слои системы (по SpecRails Reference Architecture)

```
┌─────────────────────────────────────────────┐
│  CLI (src/cli.ts)                           │
│  Точка входа, оркестрация repair loop       │
└─────────────────┬───────────────────────────┘
                  │
    ┌─────────────┴──────────────┐
    │                            │
┌───▼──────────────────┐  ┌─────▼──────────────────┐
│  Parser              │  │  Process Core          │
│  (Process Layer)     │  │  (Core Layer)          │
├──────────────────────┤  ├────────────────────────┤
│ • AI интерфейс       │  │ • Validator            │
│ • Contract Registry  │  │ • Normalizer           │
│ • Провайдеры         │  │ • YAML Emitter         │
│ • Mock AI            │  │ • Types/Errors         │
└──────────────────────┘  └────────────────────────┘
```

### Граница ответственности

**✅ Parser (Process Layer):**
- Единственная точка взаимодействия с AI
- Загрузка контрактов и JSON Schema
- Валидация ответа AI по схеме (синтаксис)
- Передача ошибок обратно в AI (repair loop)

**✅ Process Core (Core Layer):**
- Детерминированная проверка DSL (семантика)
- Нормализация структуры
- Преобразование из proposal → spec
- Генерация YAML

**❌ Что НЕ делает Core:**
- НЕ общается с AI
- НЕ принимает решений о retry
- НЕ собирает метрики
- НЕ исправляет ошибки (только находит)

## 📦 Структура пакетов

### 1. **packages/parser** — Process Layer

**Файлы:**
- `parser.ts` — основной класс Parser
- `types.ts` — ParserInput, ParserOutput, AiProvider
- `contracts/registry.ts` — загрузка контрактов и промптов
- `providers/mock.ts` — MockAiProvider (без сети)

**Ключевые моменты:**
- `Parser.run()` — единственный публичный метод
- Принимает `contractId` + `userText` + опциональные `issues`
- Возвращает `ParserOutput<T>` с `ok/data/error`
- Два уровня валидации:
  1. **AJV** проверяет JSON Schema (contract compliance)
  2. **Core Validator** проверяет семантику DSL

**Интерфейс AiProvider:**
```typescript
interface AiProvider {
  name: string;
  runStructured<T>(input: {
    system: string;
    prompt: string;
    schema: object;
  }): Promise<{ data: T; rawText: string; model: string }>;
}
```

---

### 2. **packages/process-core** — Core Layer

**Файлы:**
- `validate.ts` — validateSpecV1() + семантические правила
- `normalize.ts` — normalizeSpec() + сортировка
- `fromProposal.ts` — proposalToSpec() (proposal → spec)
- `yaml.ts` — dumpProcessYaml() (spec → YAML)
- `types.ts` — ProcessSpecV1, ValidationResult, ValidationIssue
- `errors.ts` — issue() хелпер

**Validator проверяет:**
- ✅ Тип и версия DSL (`type: process`, `version: 1`)
- ✅ Существование lanes и steps
- ✅ Валидность `entry` (должен быть в steps)
- ✅ Каждый step имеет label + lane
- ✅ Ссылки на lanes существуют
- ✅ Ссылки в `next` и `branches.to` существуют
- ✅ Шаг не может иметь одновременно `next` и `branches`
- ✅ Reachability (нет недостижимых шагов)
- ✅ Acyclicity (опционально, по умолчанию включено)
- ⚠️ Дубликаты условий в branches (warning)

**Нормализация:**
- Сортировка lanes и steps в алфавитном порядке
- Консистентное представление для YAML

---

### 3. **contracts/** — Контракты

**Файл:** `process.v1.extract.schema.json`

Определяет структуру ответа AI:
```json
{
  "entry": "step_id",
  "lanes": [{"id": "lane_1", "label": "Lane 1"}],
  "steps": [
    {
      "id": "step_id",
      "label": "Step Label",
      "lane": "lane_1",
      "next": "other_step",
      "branches": [{"when": "condition", "to": "step"}]
    }
  ]
}
```

**Важно:** Это proposal формат (массивы), не финальный DSL.  
`fromProposal.ts` преобразует его в `ProcessSpecV1` (объекты).

---

### 4. **src/cli.ts** — CLI + Orchestration

**Команды:**
```bash
node dist/src/cli.js process:extract "текст"
```

**Логика repair loop:**
1. Вызов Parser с текстом
2. Если Parser.ok → проверка Core Validator
3. Если Validator.ok → вывод YAML
4. Если Validator.errors → retry с передачей issues в Parser
5. Второй вызов Parser с теми же данными + issues
6. Финальная проверка Validator
7. Если всё ок → YAML, иначе → вывод ошибок

**Exit codes:**
- `0` — успех
- `1` — неверная команда/параметры
- `2` — первая попытка Parser провалилась
- `3` — вторая попытка Parser провалилась
- `4` — Validator не принял DSL после retry

## 🔄 Как это соотносится с идеей SpecRails

### Реализованные принципы

✅ **Core Isolation** — Core не зависит от AI, работает детерминировано  
✅ **Contract-Based Integration** — Parser возвращает DTO (ParserOutput)  
✅ **Single AI Gateway** — только Parser общается с AI  
✅ **Validation Loop** — двухконтурная проверка (schema + semantic)  
✅ **Explicit Feedback** — ошибки передаются явно в виде JSON  

### Что ещё не реализовано (но заложено в Reference Architecture)

❌ **Governance Layer** — нет метрик, политик, аудита  
❌ **Preview Engine** — нет визуализации для аналитика  
❌ **Human-in-the-loop** — нет второго контура валидации (Analyst)  
❌ **Prompt Registry** — промпты хардкоднуты в `registry.ts`, нет версионирования  
❌ **Schema Registry** — схемы не версионированы  
❌ **Observability** — нет трэйсинга, метрик, логов

## ✅ Что работает хорошо

### 1. Минималистичная архитектура
- Простые функции, понятные типы
- YAGNI и KISS на практике
- Легко читать и модифицировать

### 2. Чёткое разделение ответственности
- Parser знает про AI и контракты
- Core знает только про DSL структуры
- CLI управляет процессом

### 3. Детерминизм в ядре
- Validator даст одинаковый результат для одинакового входа
- Нет скрытых зависимостей, побочных эффектов
- Легко тестировать

### 4. Mock AI провайдер
- Можно работать без реального AI
- Быстрые тесты
- Предсказуемые результаты для разработки

### 5. Явная обработка ошибок
- Валидация возвращает список issues с severity/code/path
- Можно точно передать AI что не так
- Есть трассировка от issue к stepId

## ⚠️ Что можно улучшить

### 1. Hardcoded контракты
**Проблема:** `registry.ts` хардкодит путь к схеме и промпты  
**Решение:** Ввести Prompt Manifest (как в docs), версионирование

### 2. Нет разделения packages
**Проблема:** parser и process-core в одном монорепо без изоляции  
**Решение:** Сделать настоящие npm пакеты с package.json, отдельной сборкой

### 3. Ограниченный repair loop
**Проблема:** Только 2 попытки, нет адаптивной стратегии  
**Решение:** Добавить конфиг (max_retries), логику "сдаться раньше"

### 4. Нет типизации для proposal
**Проблема:** `fromProposal.ts` принимает `any`  
**Решение:** Сгенерировать TypeScript типы из JSON Schema

### 5. YAML emitter упрощённый
**Проблема:** `dumpProcessYaml()` использует js-yaml напрямую  
**Решение:** Добавить кастомную сериализацию для лучшего контроля форматирования

### 6. Нет тестов
**Проблема:** Всё работает, но нет автотестов  
**Решение:** Добавить unit-тесты для Validator, Parser, Normalizer

## 🎓 Архитектурные инсайты

### 1. Разделение Parser и Validator — критично
- Parser проверяет **контракт** (AI вернул что обещал)
- Validator проверяет **семантику** (DSL имеет смысл)
- Это разные уровни абстракции

### 2. Mock провайдер — must have для прототипа
- Позволяет работать без API ключей
- Ускоряет разработку
- Даёт предсказуемость

### 3. Типы первичны
- `ProcessSpecV1` — источник истины
- Все остальное (proposal, YAML) — представления
- Валидация работает с типами, не с форматами

### 4. Repair loop должен быть тупым
- CLI не знает "как исправить"
- CLI только передаёт issues обратно в Parser
- Исправление — задача AI, не оркестратора

### 5. YAGNI работает
- 700 строк достаточно для proof-of-concept
- Не нужны классы, паттерны, абстракции
- Функции + типы = понятный код
